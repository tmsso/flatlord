# Decisions — standing choices, not to be re-litigated

One line each. A session that wants to change one opens it as a question to the admin; it does not quietly pick differently. Status: **decided** / **proposed** (awaiting admin confirmation) / **open** (admin input needed before the dependent work can start).

|---|---|---|---|
| D-01 | **Drizzle for schema-as-code, migrations and the backup dump only; supabase-js for every app read/write** so RLS is always in the path. Don't add Drizzle queries in app code. | decided | Phase 0; confirmed in the 2026-09-15 review |

| D-04 | **Replace formal phase-Accept gates with the admin-actions checklist in `ROADMAP.md`.** Gates were suppressed at every transition; no phase was ever Accepted. | decided | 2026-09-15 review; admin confirmed 2026-09-15 |
| D-05 | **Due-date semantics for newly issued statements.** Today `due_date` = `due_day` of the *period* month, so a statement for August issued on 20 Sep shows "due 5 Aug" to the tenant — legally nominal, practically confusing, and it is what forced D-03. Options: (a) keep as is; (b) `due_date` = `due_day` of the month *after issue* (matches "utilities reimbursed with next month's rent"); (c) `due_date` = issue date + N days. **Decided: (b)** — `due_date` = tenancy `due_day` of the month after the issue date. Historical months keep the sheet's dates. | decided | 2026-09-15 review; admin confirmed 2026-09-15 — implement as `BACKLOG.md` B-06 |
| D-06 | **Ad-hoc notes visibility & audit.** Admin-only, or per-note tenant-visible toggle? | D-07 | **Historical statements show raw machine charge names.** Do not edit issued rows. | D-27 | **Facilities live in `inventory_items` as `kind = 'facility'`**, not a separate table; a CHECK pins them owner-owned. They reuse attachments, RLS, audit and the repair picker. | decided (owner: defaults, 2026-10-11) | Long batch 2026-10-11, PR #60, migration `0030` |

| D-30 | **Schema-dependent PRs merge only after prod has their migration**: run `migrate-prod.yml --ref <branch>` (or the top of a stacked chain) first. Adding a column is not "fail open" — selecting a missing column errors. Once prod has run a migration, it is frozen; fixes are new migrations (drizzle's migrator goes by timestamp, not hash). | decided (owner: defaults, 2026-10-11) | Long batch 2026-10-11 |
| D-31 | **Inventory `kind` is convertible** between item and facility for owner-owned rows (the owner-owned CHECK still applies); built as `BACKLOG.md` B-38. Originally proposed as "fixed at creation". | decided (owner 2026-10-12: "convertible") | PR #60; 2026-10-12 |
| D-32 | **The taxation module is an aid, not tax advice**: Hungarian defaults (15% rate, 10% cost ratio, quarterly advances) are pre-filled but every parameter is editable per year, the UI carries a disclaimer, and the module never files anything. Keep it simple — no attempt to model every rule. | decided (owner request 2026-10-12) | B-44 |
| D-33 | **Optional modules are switchable per owner**; taxation, inventory, requests and notifications default **off** for a new owner and sit under "Inactive modules" at the bottom of the menu; existing owners keep what they use. Off hides, never deletes. | decided (owner request 2026-10-12) | B-45 |
| D-34 | **Owners are isolated from each other.** An owner sees a person if it is themselves, they manage it (`persons.managed_by_person_id`, set on create) or it is linked (tenant / occupant / co-owner) to a property they own; linking a person requires seeing it already; audit rows are property-scoped (trigger-derived) plus person-visibility plus own actions. Same rule for person attachments/ID scans and invites. | decided (built; owner "defaults" 2026-10-12) | Long batch 2026-10-12, PR #78, migration `0032` |
| D-35 | **Field editability is per root property.** Global `field_policies` rows are read-only built-in defaults; at `0032` they were copied to every owned property so nothing changed for existing owners. | decided (owner "defaults" 2026-10-12) | PR #78 |
| D-36 | **The in-app backup export is "what you can see"**, run as the calling owner under RLS; the complete all-owners copy is the nightly GitHub backup only. | decided 2026-10-12 (owner confirmed the built default) | PR #78 |
| D-37 | **Module semantics (B-45):** "notifications" = the bell + automatic reminders (payment due, overdue, meter reading, contract expiry, rate review, inventory action-by); owner-initiated core emails (statement issued, notices) still go out. A property's module is on for its tenants and crons if **any** of its owners has it on; an owner's own UI follows only their own switches. A failed lookup in the cron assumes "on". | decided 2026-10-12 (owner confirmed the built default) | PR #80, migration `0033` |
| D-38 | **An owner invite without a person creates a bare person for the invitee** (name = email local part, renamed by them), visible only to them — the inviter is never asked for, and never sees, the new owner's personal data. B-42's "own personal data" step is the proper UX later. | decided 2026-10-12 (owner confirmed the built default) | PR #81, migration `0034` |
| D-39 | **With the requests module off, a tenant blocked by "≥ previous" may skip the meter directly** (D-26's note-then-skip needs a request). The missing reading still shows on the owner's verification screen. | decided 2026-10-12 (owner confirmed the built default) | PR #80 (fix found in final review) |
| D-40 | **Field-change approvals are core, not part of the requests module.** With requests switched off, personal-data change approvals stay in the owner's queue and their `/requests/<id>` page stays reachable; every other request is hidden (data kept, D-33). With requests off, an inventory discrepancy opens no request — it stays on the reconfirmation card and the owner email still goes out. | proposed — built default 2026-10-15, owner to confirm | PR #87 (B-48) |
| D-41 | **The overdue alert fires once per statement** (the first daily run on which it is overdue), not every day it stays unpaid. The dashboard's overdue card carries the ongoing state. A repeat policy (e.g. weekly) would be a new decision. | decided (owner default 2026-10-15) | PR #84 |
| D-42 | **`cron_runs` is an operational table with no `property_id`** — a deliberate exception to "every table is property-scoped" (CLAUDE.md §3.1/§6): service role only (RLS on, no policies, no grants to app roles). Manual cron triggers log as `daily-reminders:manual`; the health check judges scheduled runs only. | decided (owner default 2026-10-15) | PR #86 (B-50), migration `0036` |
| D-43 | **Rates are append-only and month-granular.** A new rate starts on the 1st of a month and closes the open one on the last day of the previous month; it may not start before an existing rate, in or before the last issued statement's month, or in or before an open draft's month (drafts freeze their lines). Billed months change only through adjustments (D-24). | decided (built 2026-10-15 within §3.3) | PR #89 |
| D-44 | **Offboarding (B-43) has no wizard table.** Progress is derived from the database; the wizard's own records ("started, end date X", a skipped step with its required note, the handover note, "pro-rata credit added") are append-only `audit_log` rows on the tenancy, latest per step wins. The **final statement** is the move-out month's statement issued *after* offboarding started; one issued before can't be amended (D-24), so the owner settles the difference separately and skips the step with a note. A **mid-month end** gets a wizard-proposed pro-rata credit (rent × unused days ÷ days in month, rounded) as a negative adjustment on the rent charge type, which the owner confirms; the engine itself still never prorates. **Ending** sets the tenancy to `ended` and revokes unused tenant invites; the proxy signs a tenant out only when they have ≥ 1 tenancy and every one is ended/terminated (a failed query or no tenancy lets the request through). Nothing is deleted. | proposed — built default 2026-10-22, owner to confirm | B-43 |
| D-45 | **"Settle from deposit" records two rows per unpaid statement**: an `applied` deposit transaction linked to the statement and a matching payment (method `other`, noted as deposit), so the statement's status follows. The deposit step is done only when the deposit balance **and** the outstanding amount are both zero. Scoped to the offboarding wizard; the plain deposit form still records ledger rows only. Alternative: make every `applied`-to-a-statement transaction create the payment (a global change — would need a look at historical deposit-offset months first). | proposed — built default 2026-10-22, owner to confirm | B-43 |
